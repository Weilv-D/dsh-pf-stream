# 发布规范

本文档是可执行的发布契约。流水线（`.github/workflows/publish.yml`）实现本契约；守卫、构建、发布三段任一失败即中止发布。

## 1. 版本源

- `package.json` 的 `version` 字段是唯一人工版本源。tag 名、GitHub Release、npm 版本全部由它派生。
- 正式发布版本号不含预发布后缀。预发布版本（`X.Y.Z-rc.N`）由维护者本地执行 `npm publish --tag next`（交互式 OTP）；Release 流水线不处理预发布版本。

## 2. 版本策略

- 版本号遵循语义化版本。0.x 阶段约定：
  - `minor`（0.1 → 0.2）：破坏性变更或新增能力（新画布形态、新 action、新配置项）。
  - `patch`（0.1.0 → 0.1.1）：缺陷修复。
  - 宿主（DSH GUI）集成验证通过后升 `1.0.0`。
- 仅文档变更合入主干，随下一个版本发布；纯文档变更不单独发版。

## 3. 发布流水线

固定环境：runner `ubuntu-24.04`；Node 22；pnpm 9；npm 11（publish 段）；ffmpeg/ffprobe 由 apt 安装并打印版本。

三段 job，权限最小化（顶层 `permissions: {}`，仅 publish 段持 `id-token: write`）：

| job | 权限 | 职责 |
| --- | --- | --- |
| `guard` | contents: read | 四项守卫：tag 等于 `v{version}`；版本号无预发布后缀；Release 非 draft、非 prerelease；tag 提交在 `main` 历史内 |
| `build` | contents: read | 安装依赖 → 构建 → 包内容白名单审计 → `npm pack` 产出 tarball → 上传 artifact → 全量测试（含 e2e）→ 宿主契约自检 |
| `publish` | id-token: write, contents: read | 下载同一 tarball → `npm publish <tarball> --provenance` → 发布后验证 |

- 发布物唯一来源：`build` 段产出的 tarball（artifact）。`publish` 段仅发布该 tarball；测试过的就是发布的。
- 包内容白名单：`package.json` 的 `files` 数组（`lib/`、`cordis.patch.yml`、`LICENSE`、`README.md`、`README.en.md`）。审计脚本 `scripts/check-package.mjs` 逐条比对 `npm pack` 产物。
- 并发控制：`concurrency: publish-{ref}`。同一 Release 至多一个发布流程。
- 超时：guard 5 分钟、build 20 分钟、publish 10 分钟。

## 4. 发布后验证（流水线内置）

- `npm view dsh-pf-stream@{version} version` 精确命中。
- `dist-tags.latest` 指向该版本。
- `attestations`（provenance）存在。
- 任一项失败，publish 段标红。

## 5. 环境绑定一致性

- npm Trusted Publisher 与 workflow 两侧一致：当前均为空 Environment。
- 备选增强：两侧统一 `npm-publish`，并在 GitHub Environment 配置保护规则。二选一；只改一侧会使发布被拒。

## 6. 发布步骤

1. `main` 升版本并推送：

   ```powershell
   npm version patch   # 或 minor
   git push --follow-tags
   ```

2. 等待该提交 CI 绿。CI 门禁与发布流水线一致（同脚本、同审计）。
3. GitHub → Releases → Draft a new release：
   - Choose a tag：输入 `v{版本}`，目标选升版提交（main HEAD）；
   - 填写变更要点；
   - Publish release。
4. `publish` 工作流自动执行 guard → build → publish。
5. 复核：Actions 三段全绿；npm 页面版本、latest 标签、provenance 徽标。

## 7. 失败处理

发布前失败（npm 上无该版本）：

1. 修复缺陷并合入 `main`。
2. 删除该 Release 与 tag。
3. 版本号升 patch，重走发布步骤。
4. tag 不改指向；失败版本号作废。

已发布缺陷：

1. `npm deprecate dsh-pf-stream@{版本} "原因"`。
2. 发新 patch 版本。
3. npm 已发布版本固定；覆盖与删除均不可用。

## 8. 审计链

每个正式版本对应四元组：npm 版本 = tag `v{版本}` = 升版提交 = CI 构建的 tarball。provenance 证明 tarball 构建来源。发布历史可在 Releases、Actions、npm attestations 三处交叉核对。
