# 发布规范

一句话：**npm 上有没有这个版本，只有"发布成功"一个来源；其余一切（tag、Release、流水线绿）都不能代替对 registry 的直查。**
本文是版本发布的唯一操作依据：升型决策 → 发布前检查单 → 升版推送 → Release 与流水线 → 发布后核验 → 失败处置。每一步给出「做什么、怎么验证、失败走哪条分支」。

---

## 1. 总则

- **版本源**：`package.json` 的 `version` 是唯一版本源；tag 名（`v{版本}`）、GitHub Release、npm 版本全部由它派生。
- **触发权**：发布由维护者明确指令启动；开发完成不自行发布（交接文档 §10 纪律）。开发批次完成时停在「发布前检查单第 0 步之前」，等指令。
- **审计四元组**：每个正式版本对应 npm 版本 = tag `v{版本}` = 升版提交 = CI 构建的 tarball；provenance 证明构建来源。发布历史在 Releases、Actions、npm attestations 三处交叉核对。
- **预发布版**（`X.Y.Z-rc.N`）：维护者本地 `npm publish --tag next`，不走流水线。

## 2. 版本升型决策表

先定升型，再动手。0.x 阶段（宿主集成验证通过后升 `1.0.0`）：

| 变更内容 | 升型 | 例 |
| --- | --- | --- |
| 缺陷修复、内部重构、遥测/文档注释补全 | patch（0.3.3 → 0.3.4） | 审计修复批次 |
| 新增用户可见能力（新工具/新 action/新配置项/新宿主集成） | **minor**（0.3.4 → 0.4.0） | storageDomain 落盘接线 |
| 破坏性变更（工具契约、Config 删除/改义、宿主版本下限上调） | minor，且正文列「破坏性变更」小节 | 未来 engines.dsh 下限上调 |
| 仅文档变更合入主干 | 随下一个版本发布，不单独发版 | 表格对齐类提交 |

判定口径：**看模型/用户可见行为差**，不看改动文件数。拿不准时选 minor——0.x 阶段 minor 与 patch 的成本差为零，虚低升型才会造成混乱。

## 3. 发布前检查单（全部完成后才允许升版）

按序执行，任何一步不过则停下修复后**从头重跑本检查单**：

1. **四门禁全绿**（工作区含本次全部改动的状态下）：

   ```bash
   pnpm build          # tsc 0 错误
   pnpm test           # 全量用例通过（记录用例数/文件数）
   pnpm verify:host    # 宿主契约自检通过（记录项数）
   pnpm check:package  # 包内容与 files 白名单一致（记录文件数）
   ```

2. **文档同步**：使用指南/排障/README 中与本次变更相关的条目已更新，与实现逐条对应（交付前自查承诺与实现一致）。
3. **交接文档**（本地文件，git 不跟踪）：版本链行、开发历程条目、待办勾销已更新。
4. **工作区干净**：`git status` 干净；交接文档确认在 .gitignore 中。
5. **升型已定**：按 §2 既定升型，下一版本号已明确。

## 4. 升版与推送（一条命令，不 amend）

> 历史教训（交接文档 T40）：`npm version` 缺省提交信息是裸版本号（"0.3.4"），与仓内惯例（`release: X.Y.Z`）不一致 → 事后 amend 提交 → tag 指向旧提交 → 重建 tag → `--follow-tags` 未推送重建的 tag。整条链每一环都是可避免的。

**正确手法是一次成型，禁止事后 amend**：

```bash
npm version minor --message "release: %s"    # 提交信息与附注 tag 消息同时为 release: X.Y.Z
git push origin main vX.Y.Z                  # 提交与附注 tag 一条命令显式推送
```

- `npm version --message` 让提交与附注 tag 一次成型；**禁止先升版再 amend 提交信息**（amend 必然使 tag 指向旧提交）。
- tag 由 `npm version` 自动创建为**附注 tag**；禁止手工建轻量 tag。
- 推送用**显式 tag 名**（`git push origin main vX.Y.Z`），不依赖 `--follow-tags`。
- 验证：`git describe --tags --exact-match HEAD` 输出 `vX.Y.Z`；`git ls-remote origin vX.Y.Z` 输出升版提交哈希。

## 5. Release 与流水线

1. **等升版提交的 CI 绿**（该提交会触发常规 CI；发布流水线由 Release 创建触发）。
2. **创建 GitHub Release，绑定已存在的 tag，不填 target**：
   - 教训（0.3.4 实录）：`npm version` 已创建 tag；Release 再指定目标提交会 422（`Release.target_commitish is invalid`）。
   - CLI：`gh release create vX.Y.Z --title "vX.Y.Z" --notes "<变更要点>"`（tag 已存在时直接绑定，无需 --target）。
   - Web：Releases → Draft a new release → tag 选已有 `vX.Y.Z` → Publish。
   - Release 正文写变更要点（可取自发布提交的提交信息正文）。
3. **流水线三段**（`.github/workflows/publish.yml`，Release 创建自动触发）：

| 段 | 权限 | 内容 | 超时 |
| --- | --- | --- | --- |
| 守卫 | contents: read | tag 等于 `v{version}`；版本号无预发布后缀；Release 非 draft、非 prerelease；tag 提交在 `main` 历史内 | 5 分钟 |
| 构建 | contents: read | 构建 → 包内容白名单审计 → `npm pack` 产出 tarball → 上传 artifact → 全量测试（含 e2e）→ 宿主契约自检 | 20 分钟 |
| 发布 | id-token: write | 下载同一 tarball → `npm publish --provenance`（Trusted Publishing OIDC）→ 发布后验证 | 20 分钟 |

- 发布物唯一来源是构建段产出的 tarball，发布段只发布该 tarball。
- runner `ubuntu-24.04`；Node 22；pnpm 9；npm 钉扎精确版本（发布段 `npm install -g npm@11.10.1`，升级走显式提交，防浮动安装污染 id-token 上下文）；ffmpeg/ffprobe 由 apt 安装。
- 权限最小化：顶层无权限；仅发布段持 `id-token: write`。
- 发布流程全仓串行（concurrency 组 = 仓库级）：两个 Release 并发发布时，后落库的低版本会把 `dist-tags.latest` 拉回且流水线零信号（全绿静默回退），仓库级串行消除该角落；逐 Release 核验后再发下一个仍是纪律底线。

## 6. 发布后核验清单

流水线绿之后逐项核验，任何一项失败走 §7：

1. **Actions 三段全绿**（记录 run id）。
2. **registry 直查**（唯一权威）：

   ```bash
   npm view dsh-pf-stream@X.Y.Z version dist-tags.latest
   # 期望：version = X.Y.Z 且 dist-tags.latest = X.Y.Z
   ```

3. **provenance**：npm 页面该版本有 Provenance 徽标；发布日志含 sigstore transparency log index。
4. **本机生效**：desktop profile 重装——

   ```bash
   dsh plugin --profile desktop remove dsh-pf-stream
   dsh plugin --profile desktop add dsh-pf-stream@X.Y.Z
   ```

   重启 DSH 后工具可用（升级后必须重启应用，宿主缓存进程内模块）。

## 7. 失败处置（按阶段分类）

### 7.1 发布前发现缺陷（registry 上无该版本）

1. 修复缺陷，四门禁全绿后合入 `main`。
2. 删除该 Release 与 tag：`gh release delete vX.Y.Z --yes && git push origin :refs/tags/vX.Y.Z`。
3. 版本号作废，用新 patch 版本重新走 §3–§6。tag 不改指向。

### 7.2 发布中：验证段失败 ≠ 发布失败

**先分清「发布失败」与「发布后验证误报」**——判定口径只有一条：`npm view dsh-pf-stream@X.Y.Z`。

- **registry 已有该版本**（0.3.4 实录：publish 实际成功，registry 元数据传播超过旧 5 分钟观察窗）：
  1. 确认 `dist-tags.latest` 已指向该版本（直查，勿信流水线红叉）。
  2. 按幂等设计重跑失败段：`gh run rerun <run-id> --failed`（registry 已存在该版本时 publish 步骤自动跳过，只执行验证；若首查 404 但 `npm publish` 报版本已存在，步骤会复查 registry 并按已发布继续）。→ 已固化为流程一部分，不再算事故。
- **registry 无该版本**（真失败）：publish 步骤日志找原因（OIDC/网络/包问题）；若日志为 TLOG 409，按 §7.4 重跑同一 run；其他原因修复后按 §7.1 作废重来。

### 7.3 已发布缺陷

1. 先 `npm deprecate dsh-pf-stream@{版本} "原因"`，让新安装看到迁移提示。
2. 尽快发新 patch 修复；不要试图用 `npm publish` 覆盖同版本，npm 会拒绝。
3. `npm unpublish` 只在确有安全或合规必要时使用，通常仅限发布后 72 小时内、按 npm 政策执行。撤下会永久占用该版本号（不能再发布同号），并可能影响已锁版本的安装；普通缺陷用 deprecate + 新版本，不要撤版。

> 0.4.0 实录：因实际会话修复未包含，发布后约 3.9 小时撤下；0.4.0 从此 404 且不可复用，修复以 0.4.1 重新发布。

### 7.4 发布段报 TLOG 409

**现象**：`npm publish --provenance` 失败，日志含 `TLOG_CREATE_ENTRY_ERROR` 与 `(409) an equivalent entry already exists in the transparency log`；`npm view dsh-pf-stream@X.Y.Z` 仍 404。

**处理**：

1. 不要立刻升版本号；先直查 registry 与 provenance，确认版本是否真的不存在。
2. 这是 transparency log 已有等价条目、registry 尚未可见的竞态。对同一 run 执行 `gh run rerun <run-id> --failed`，不要新建 Release 或改 tag。
3. 重跑成功后按 §6 核验；0.4.1 实测一次重跑即成功。
4. 连续两次重跑仍 404，才按 §7.1 作废 tag/版本，改用新 patch。

## 8. 发布后记录

- 交接文档：版本链行（`| X.Y.Z | 升版提交 | 摘要 |`）、开发历程条目（含门禁实测数）。
- 记忆文件：版本状态行更新。

## 9. 附：流水线可靠性参数

- 发布后验证 `scripts/verify-release.mjs`：分级轮询窗口 **15 分钟**（10s×12 → 20s×15 → 30s×16），单次 registry 请求 5s 超时，另有 14 分钟进程级软截止（43 次全部 5s 超时的病态场景下宁可干净 exit 1 可 rerun，不拖到 job timeout 强杀）；判定条件是版本存在且 `latest` 已到达/超过目标版本（并发发更高版本时不误报；latest 为 prerelease 等非正式版本号时按不高于放行并告警）。依据：0.3.4 实测 Trusted Publishing 下 registry 元数据传播 >5 分钟；旧 5 分钟窗口会误报失败。发布段超时同步放宽到 20 分钟。
- 发布步骤幂等：registry 已存在该版本时跳过 `npm publish` 只执行验证；若首查 404 而 `npm publish` 报版本已存在，脚本复查 registry 后按已发布继续。重跑（`gh run rerun <run-id> --failed`）是安全操作，优先重跑而不是作废版本号。
